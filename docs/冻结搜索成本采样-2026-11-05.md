# 冻结搜索成本采样（2026-11-05）

## 发现与决定

实际采样支持先核查结果档案的序列化深拷贝成本。它是四职责与匹配NSGA-II的共同成本，并未解释两者同FE质量差距。未实现提速、未报告同时间优势，也未将工程机会作为新算法创新。

[协议、实际类来源、JFR、原始采样和验收](../runs/frozen-cost-profile-20261105-045842-495438/)。复用两开发实例、旧seed10950003、旧500,000FE账本，运行冻结 `STRICT_FULL` 与 `NSGA_STRICT`，不改任何搜索类，主线未变。仅前置一个类身份读取工具，已确认四份原命令classpath一致。

## 费用与观测验收

四条各500,000成功FE，共 **2,000,000成功FE，0失败**。返回解另1,962次完整解码QA。每条初始四向量、物理账本、最终编码、所有已登记FE前沿、搜索计数和增量复用/重算操作数均与原性能轨迹一致。

原性能轨迹未记录完整付费序列SHA，因此这次只主张上述观测等价，**没有证明每个付费候选序列逐个相同**。没有借JFR结果改算法或反馈搜索。

仅使用本机既有JDK17 Flight Recorder，profile设置、栈深128、每份JFR上限32MB，JVM顺序执行；没有安装、下载、上传或远端中转。JFR导出的JSON因重复栈信息会大于二进制记录，不是下载流量。

分配采样weight是抽样估计，不是峰值内存、精确累计分配或持续占用；不能把weight汇总的GB数解释为电脑需要同样大小RAM。其他明显成本包括编码合法化、解对象构造、增量解码及DynamicSchedule汇总；没有证据直接优化或更改这些逻辑。

## 下一项等价工程假设

当前 `SolutionSnapshots.copy` 序列化整个可序列化图，深拷贝同时保证未知可变属性、四向量和辅助字段独立。不能简单改成现成 `solution.copy()` 或浅拷贝。

可单独验证的方案是：**保留Java序列化对可变图的复制，仅让经过审计的final不可变上下文通过临时引用句柄共享**。实际模型的Instance、DynamicParameters、DynamicSchedule/Step、SchedulingMetadata是候选白名单；还需核查实际类的封装和无自定义序列化回调。未知类型和可变DynamicPrefix不得共享，白名单按精确类判断。

这项修改只在隔离副本，以旧SERIAL为默认、ANCHOR为显式试验模式。工程前提包括：未知可变属性和循环/别名关系仍正确深拷贝；源解、返回快照及不同返回快照之间的可变数组/列表/属性互不污染；完整解码物理时间轴不变；失败仍不破坏旧档案。然后在共同输入、seed和账本下，逐项验证接受计数、完整付费序列摘要、全部FE前沿和最终编码。

只有工程完全等价，才关闭观察成本，给四职责及经典对照同时使用同一实现，测实际吞吐和真正TIME_LIMIT。即便共同提速成立，也不能代替四职责/共享必要性、同预算质量、独立实例确认或新颖性证据。研究goal保持active，尚无合格完整算法。
