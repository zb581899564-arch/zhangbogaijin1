# 固定供体支持域穷举与下一步（2026-11-06）

后续勘误：通用支持域辅助函数原将相等优先键按job升序处理，实际TypedScheduleGenome按job降序。六份真实来源经核查均无跨工件相等键，故本页穷举结果及成员分类不受影响。当前辅助源码已修正，原运行快照保留；明确平局夹具与零FE更正见[下一轮协议](固定FA域外生产验证协议-2026-11-06.md)。

**本轮把一个失败原因查实了：在三个预定的20工件成熟家族里，当前五个供体能表达的全部组合都没有额外档案价值。停止在这个固定域内继续改接受规则。** 这不否定四子群及原共享，也不是对整个20工件实例、所有家族或100工件实例的穷举。

## 做了什么，为什么不是重复旧试验

延续[真实请求约束生产失败](真实共享请求约束供体生产结果-2026-11-06.md)，使用同一Linux冻结模型、两个开发实例和三个已有seed，取每份来源事前固定的q0/ROLE入口五个成熟供体，不按质量选家族。前次cap优先探针改变了373次接受却没有实质增量，本轮检验“是接受没找到好组合，还是组合域本身已经没有价值”。

- 旧工厂池闭包组合**已经存在的完整厂内记录**。本轮枚举每个工件从五个成熟供体继承的`(资源元组, priority key)`，因此包含池里没有的厂内重组。
- 保留固定FA，不生成新资源或新键。原GOM的配对复制保持这个域封闭。静态枚举忽略接受限制和活供体丢失，是表达范围的上界，并不证明动态过程能到达全部组合。
- 20工件的15个工厂合计185,775种潜在继承选择，去重为3,580种厂内物理日程。100工件组合过大，只做已付费候选成员关系核查，不冒称穷举。
- 每个新厂内日程嵌入完整合法排程，经共同`RunContext`真实计费。之后用局部目标的精确二进制有理数及Pareto动态规划组合完整目标；代数展开与完整解码分别计账。
- 本轮不是同预算算法对比，不把穷举解注入生产档案，不宣称同时间优势。四职责、QGS、固定家族及原共享代码均未改。

## 对瓶颈的新认识

当前资源候选已明显收缩：20工件三个家族分别有17、11、12个工件只剩一种机器—工人元组；100工件对应61、92、78个。除一个100工件初始家族有1个单元组工件外，其余初始家族均为0。这个事实说明“更改接受后仍只能在很窄的资源范围里组合”，但**多样性减少本身不是质量损失的因果证明**。

六个家族的FA均与初始化相同。不过算法另有80个自由粒子，不能把整个搜索称为FA冻结。本轮同时固定了FA、资源候选和顺序键，不能仅凭闭包失败判断必须更改FA。

为核查这一边界，又做了[零FE同FA见证审计](../runs/linux-family-support-closure-20261106-01/same-fa-witnesses.json)：取六个来源之前最近的已付费250k检查点，全部检查同FA前沿解。100工件/16110037有38个，只有5个在当前五供体支持域内，33个在域外；但没有一个严格支配任一当前成熟供体。其他五个上下文没有同FA见证。它证明当前域不覆盖所有已知同FA结构，**不能证明历史供体能改善A0，也不能据此复活档案重启**。此项是看完边界结果后的探索性补充，不伪装成预登记性能终点。

## 下一步怎样收敛

下一个值得讨论的问题是：**保持同一FA，直接生成当前供体域之外的新合法资源—顺序结构，是否存在实质容量？** 先回答这个必要条件，再讨论生产机制；不继续调供体比例、cap、接受平局或局搜轮数。

与旧失败的区别必须落实在代码语义：

|旧方案|已测内容|下一假设必须新增的事实|
|---|---|---|
|DEMAND / cap优先生产|路由或接受变化，当前继承式候选域不变|生成范围真正超出当前资源—键支持域|
|TYPED字段解绑|拆分机器/工人继承字段及访问，匹配SHAM仍退化|不能只是再拆字段或增加访问；须先有域外物理质量见证|
|普通合并供体、档案FI/重启|整个已付费状态的引入或替换|不能把旧解的回流当作新增档案价值|
|ELITE/RANDOM家族刷新、家族释放|更换FA或解除约束，旧固定版本未过|当前没有复活依据；先区分同FA生成不足与FA本身限制|

新试验还未登记、未启动。最小设计应先固定相同FA和成熟入口，拿域外生成与普通合法生成作对照；所有完整或前缀物理查询均计费并单列，不能把离线构造免费藏在算法里。只有出现超过当前域且对A0有实质价值的见证，才设计同预算闭环并评估四职责的额外作用。这是下一问题，不是已发现的新算法或创新性证明。
