# 动态疲劳增量重算 v4：实现提速和同时间增益成立，疲劳反向尚未胜过时间通道

本轮完成了受影响工厂/不变前缀的精确重算。**增量实现保持完整首阶段的数值和搜索轨迹，并在相同时间下优于对应完整实现；完整疲劳伴随仍没有显示优于共享增量内核的时间通道。** 这两条结论必须分开，不能把工程提速归为疲劳反向的独立贡献。

原始证据：[正确性阶段](../runs/fatigue-incremental-validation-v4-20261031-175339-612108/completion.json)、[性能目录](../runs/fatigue-incremental-performance-v4-20261031-175805-055200/)、[完整机器汇总](../runs/fatigue-incremental-performance-v4-20261031-175805-055200/summary.json)、[全部单元表](../runs/fatigue-incremental-performance-v4-20261031-175805-055200/report.md)、[记录审查](../runs/fatigue-incremental-performance-v4-20261031-175805-055200/audit.json)。设计见[运行前协议](动态疲劳增量重算协议-v4.md)。

## 先确保精确，再验证性能

对每个父本工厂保存 `(job,machine,worker)` token序列、首阶段C/v与逐工序能耗/工资、每个前缀后的机器/工人最后工序id。未变工厂直接复用；变动工厂从第一个不同token开始，恢复资源前驱快照，复用完全相同的前缀，真实计算整个新后缀。没有近似收敛截断。逐工件FA修改当前明确拒绝。

费用仍按完整重算的工厂/序列顺序相加，避免浮点累加顺序影响平局；未变前缀的疲劳状态也复用，不能只复用完工时刻。候选参数/实例在一条链内固定，接受新父本后前缀与伴随均失效。

- 新增8项检查及2项共享局部链回归检查通过，覆盖首/尾修改、局部邻域、多厂变化、跨厂全局交错不变、FA拒绝、缓存不变性、初始疲劳/参数极限、数值/轨迹、截止处理和重复统计单位。
- 先用旧seed的90场景、540个连续变化父本做8640候选比较，C/v/直接费用均与完整首阶段重算**逐位相同**；工作量守恒全部通过，540个父本时间轴合法。
- 性能入口核对已验证核心源码和实例与当前文件逐字节相同，通过后才使用新seeds **23、53、97、193、389**。
- 新seed性能共1800条链、93022步、26393缓存周期全部通过记录/版本/截止和工作量审查；1800个最终调度离线完整解码核验。60对固定步数完整/增量实现的分数、选择、接受及最终路径全部逐位一致。

代码位于 `research/fatigue_incremental/`。共享v3局部链只增加可选评分引擎和工作量日志，默认原评分路径通过回归检查；四轮源码均随运行保存。Java模型、PSO、QLS/QGS和整套算法未改。选中子本仍使用共同完整动态解码器评价；本次增量加速的是**评分所需首阶段**，没有把完整后阶段候选评价替换为近似。

## 提速来自哪里

90个初始候选池的独立校准（一次预热+5次测量的case中位数再平均），16候选完整数值首阶段为 **4.363ms**，增量版为 **1.397ms**，平均时间之比约3.12。前缀快照结构本身建立约0.075ms；伴随计算的其他费用另在在线缓存构建时钟内，没有免费省略。

主要限时单元中，疲劳法实际递推481860道工序，完整重算等价为2539520道，比例 **18.97%**；15.11%复用了不变前缀，65.91%属于未变工厂。实际复制、检查、token扫描、费用汇总和投影仍存在，不能把少算81%的物理递推声称为总费用也少81%。

同一主要场景固定24决策时的实现对照如下，所有版本最终目标和轨迹完全一致：

|方法|完整首阶段总时间|增量首阶段总时间|完整/增量总时间中位比|
|---|---:|---:|---:|
|疲劳边界|216.99ms|156.05ms|1.341|
|时间边界|201.68ms|150.23ms|1.339|

缓存维护和前缀构建已计时，增量实现总时间中位加速约1.34倍（约25%的时间缩减，不能说缩减34%）。疲劳法平均节省60.95ms，时间法51.44ms。

## 疲劳、时间和随机：疲劳反向没有胜出

主要单元每父本限时重复3次，随机流相同；先在父本内平均，再按6实例×5seed分层配对bootstrap2000次，独立父本数仍为30。三档疲劳、两个方向和两种预算全保留，未按结果换主要单元。

|主方法|三次平均最终收益|完整实际耗时，含尾部|准时完成决策|
|---|---:|---:|---:|
|增量首阶段+疲劳边界|14.815%|253.13ms|53.28|
|共享增量首阶段+时间边界|15.301%|252.58ms|54.82|
|原廉价时间通道|14.111%|252.50ms|60.52|
|相同合法局部池规则随机|11.087%|251.21ms|125.79|

疲劳法相对时间边界平均 **-0.4861个百分点**，配对区间[-1.7288,+0.3580]；相对廉价时间通道+0.7045个百分点，区间[-0.7862,+1.7809]；相对随机+3.7284个百分点，区间[+1.4618,+6.1307]。按全部实际耗时计算的收益率差也呈同样判断。

疲劳法相对共享增量时间边界的三次单独重复差为-0.480、-0.465、-0.513个百分点，三个区间均跨0；没有由时钟重复改变为稳定的疲劳法优势。在所有预先保留单元中，也没有其相对共享时间边界的收益差区间完全高于0。不能为了强调梯度，改用只有更弱随机控制的结论。

补充的**事后归因性比较**显示，增量时间边界相对廉价时间通道+1.1906个百分点，区间[+0.5537,+1.9171]；相对随机+4.2146个百分点，区间[+1.7106,+6.6706]。这提示精确增量首阶段+时间边界值得作为后续主候选，但该额外对比未预先指定为主要检验，需独立确认，不能当作已确定的发表级贡献。记录见 `additional_time_control_contrasts.json`。

## 费用与复用仍是实测结果

疲劳法主要单元中，增量内核约占在线时间19.77%，缓存建立16.46%；费用包含候选检查、前缀定位、数组复制、精确汇总和工作量记录。完整首阶段实现的首阶段约占41.02%，但它只有repeat0；总实现效果优先看前述严格配对消融。

90条主要重复链的2141个缓存周期平均q=2.282、中位数1，q>=4比例10.70%；接受终止周期平均q=1.887，预算结束右删失周期已观察q平均11.27。高q仍主要出现在不再接受新父本的尾部，不能重新假定每次改进都能复用4/16次。

## 完整口径和边界

性能轮在线搜索计时合计358.19秒，含校准/离线QA/输出的整轮壁钟497.58秒，另有先行正确性阶段约5.61秒。单进程单线程，运行结束后正常退出，没有后台服务。

- 性能轮在线完整评价94822次，首阶段部分评价627456次，缓存建立26393次；主比较、重复和实现消融合计，不能冒充某一方法单次预算。
- 独立校准增量/完整首阶段各10080次，前缀结构建立630次，初始trace完整90次、minimal/trace计时各540次。
- 离线最终调度完整核验1800次、候选/接受/截止逻辑重建93022步，不反馈选择；JSON输出另记约3.07秒。

所有在线初始化、生成、缓存/失效、增量重算、伴随、投影、选中子本完整解码和内存审计都在时钟内。末次非抢占超时费用计入实际收益率，但超时完成的改进不进入0.25秒成绩。公共加载、独立校准、磁盘输出和离线验证按先前协议另计。

当前仍是FA固定的首阶段局部编辑；没有验证FA迁移、增量完整后阶段解码、主动休息/插空、真实人体参数、全多目标优化器或HV/IGD+。限时轨迹依赖本机实际运行负载，已做主要单元三次重复和轮换顺序，尚无跨硬件结论。

目前应保留增量内核及时间通道作为更有依据的研究对象，完整疲劳伴随继续作为消融/对照；不把它直接接入整套算法，也不把这次实现提速包装成已确认的疲劳算法创新。
