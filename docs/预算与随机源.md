# 严格 FE 预算、结果档案与随机源

本文件说明公共运行组件的语义及基线接入点。组件位于 `src/java/runtime/`，包名为 `org.uma.jmetal.util.research.runtime`，兼容 Java 8。它是工程修复，不是新算法贡献，也不证明论文语义已经全部复现。

## FE 的计数边界

`BudgetedProblem.evaluate` 是唯一允许进入真实解码器的入口：先检查剩余预算并消耗一个 FE，再调用原问题的 `evaluate`，最后验证真实三个目标并维护独立档案。初始化、全局搜索、局部搜索、候选拒绝前的评价和修复后的再次评价，只要进入真实解码器都使用此入口。对同一对象的重复解码也重复计费；本组件没有缓存。

`EvaluationBudget` 使用非负 `long` 上限，分别保存 `attempted()`、`successful()`、`failed()` 与 `remaining()`。一次 `evaluate` 已获得预算后，即使解码器抛出异常、返回非有限目标或无法生成独立档案快照，这个 FE 也不退还，并记为 failed。预算耗尽时，在下一次真实解码之前抛出 `BudgetExhaustedException`；被预算拒绝的调用没有执行解码，不增加 attempted 或 failed。正常单线程调用返回后满足 `attempted = successful + failed`。

`RunContext.run` 只捕获属于本次预算的 `BudgetExhaustedException`。普通解码异常、非法目标、快照错误及其他运行错误原样向外传播，不能将失败实验记作成功完成。入口应保存异常、三个计数以及当前可获取的档案，再将该次运行标为失败。

预算为 0 时 `RunContext.run` 不执行算法并返回空档案。预算为 1、小于初始种群、恰好结束于初始化或者在一代内部耗尽时，都允许立即返回已有档案，无须完成整个种群或整代。旧算法的 `currentIteration`、`QN * swarmSize` 等估计计数不再充当 FE 证据；严格计数以包装问题为准。

## 返回值必须来自独立档案

`ThreeObjectiveArchive` 仅接纳 `BudgetedProblem` 中已经完成评价、且目标数量恰为 3、三个目标均有限的解。三个目标按索引 0、1、2 统一最小化；不将辅助工厂索引当作目标。它保存所有成功评价候选中的非支配结果，包含最终未被旧算法接受的候选；这项统一外部档案策略必须在各比较算法间保持一致，并作为修复版协议公开。

档案不设置容量上限。同一目标向量只保留首次成功进入档案的代表，按 double 的精确值去重，没有加入影响 Pareto 关系的容差。每次候选可能入档时才制作快照，被当前档案支配或目标完全重复的候选不制作快照。

为避免 `Solution.copy()` 对辅助向量或嵌套属性的浅复制，快照使用 Java 序列化复制整个 solution 对象图；取出结果时再次复制。目标、四条编码向量、附属属性及非静态问题字段不与继续搜索的对象共享。solution 对象图必须可序列化，不能在属性中放入未实现 `Serializable` 的运行资源。该机制不复制或隔离 Java 静态字段，不支持据此在一个 JVM 并行评价多个问题实例。

档案比较、序列化及结果复制不调用解码器，所以不计 FE；其时间和内存成本必须计入同时间比较并单独说明。整个问题对象图可能较大，尚未测量正式规模下的档案开销。今后若改成专用四向量快照，须保留相同的独立性和目标语义并重新验证。

预算中断时旧算法的 swarm、分群、历史最优中可能含有未评价或已修改但尚未重评的候选。结果应始终取 `context.result()`，不能在 catch 后继续返回旧算法的 `getResult()`。空档案也是有效的 FE=0 结果，不应为填补返回值偷偷追加评价。

## 最小接入

```java
Problem<PermutationSolution<Integer>> rawProblem = /* 当前章的三目标问题 */;
RunContext<PermutationSolution<Integer>> context = new RunContext<>(rawProblem, feLimit, seed);
MOPSODivSubDE algorithm = new MOPSODivSubDEBuilder(context.problem(), /* 原有参数 */)
        /* 原有设置 */.build();
context.run(algorithm);
List<PermutationSolution<Integer>> result = context.result();
long actualFE = context.budget().attempted();
```

全部 evaluator 调用必须接收同一个 `context.problem()`，不得在局搜中重新构造或保留未包装的原问题用于评价。可在算法停止条件增加 `context.budget().remaining() == 0` 以省去预算已满后的算子工作，但真正的硬边界仍在每次解码之前。若旧 `maxIterations` 会导致算法提前停止，应分别记录“配置 FE 上限”和“实际 FE”，不能仅以包装入口存在就声称已经消费完配置预算。QN 和局搜循环参数应照实际生效值记录，不能用声明值替代被写死后的执行值。

两章 `MOPSODivSubDE` 的活跃评价调用目前都经 `evaluator.evaluate(..., problem)`；包装构造时保存的 `problem` 可覆盖这些评价。`AbstractParticleSwarmOptimization.run()` 无须对半批结果继续初始化，只需由外层在整个 run 之外处理预算异常。公共源码需加入各章 core 的编译源码范围，两章仍分别编译和运行。

## 唯一随机流

`SeededRandom.reset(seed)` 创建一个 `java.util.Random` 流，同时将 `JMetalRandom` 的 generator 替换成适配同一流的实现。`SeededRandom.current()` 每次返回同一个 Random，不能替换成每次 `new Random(seed)`；后者会不断重启序列。`SeededRandom.shuffle(list)` 等价于 `Collections.shuffle(list, SeededRandom.current())`。jMetal 的 `nextInt(lower, upper)` 仍为两端包含。

需要迁移的调用是活跃路径中所有无 seed 的 `new Random()`、`Collections.shuffle(list)`、`Math.random()`，以及自定义 generator；相应替换为 `SeededRandom.current()`、带同一 Random 的 shuffle、`SeededRandom.current().nextDouble()`。审计范围至少包括两章 `MOPSODivSubDE`、`DefaultIntegerPermutationSolution`、活跃修复辅助函数及 `mypso/util/ReplayBuffer`。只调用 `JMetalRandom.setSeed` 无法控制其他旧随机源。

必须在第一次随机操作之前 reset；`RunContext` 的构造会 reset，若原问题构造本身需要随机数，应更早显式调用。现有不经 context 的结构检查也需在创建随机 solution 前 reset。未 reset 或从其他线程调用 `SeededRandom.current()` 会明确报错，避免悄悄回落到时间 seed。

同 seed 的复现条件还包括相同代码、参数、实例、单线程执行顺序与 JVM 环境。改变求值顺序或插入一个随机调用会改变后续轨迹。若只改变日志格式而没有随机调用，轨迹不应变化。相同 seed 不保证不同算法具有相同随机调用序列，只保证各自重复运行可复现。

## 进程与线程边界

正式入口应使用“一个章、一个实例、一个 seed、一个独立 JVM”的运行单位。旧问题的机器/工人表等静态状态尚未消除，`SeededRandom` 和 `JMetalRandom` 也属于 JVM 全局状态；不得在同 JVM 并行运行多个 context，或在仍使用旧 context 时 reset 另一个 seed。`RunContext` 只允许调用一次 run。FE 预算、创建 solution、执行 run、取出档案和随机源限制为创建 context 的单线程，不能搭配多线程 evaluator。进程隔离保证旧静态状态不会跨运行泄漏，不等于已经完成实例状态重构。
